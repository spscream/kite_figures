# kite_figures

Статический сайт-каталог обязательных фигур соревнований по спортивному кайту:
список фигур, схемы из своих данных, ссылки на официальные правила.

Это Next.js со статическим экспортом (`output: 'export'`). Бэкенда и базы нет:
содержимое лежит файлами в репозитории, сборка превращает его в папку `out/`,
и в проде эту папку отдаёт обычный статический веб-сервер. Сервер Next.js в
проде не запускается, поэтому всё, чему нужен сервер во время запроса (route
handlers, server actions, `headers()`, оптимизация картинок), здесь не
работает. Route handler годится только статический (`force-static`): он
исполняется один раз при сборке и становится файлом, как индекс поиска.

## Данные фигур

Фигуры лежат в `data/figures/`, по одному файлу на фигуру. Сайт обходит
каталог при сборке: добавить фигуру значит положить файл, никакого списка
фигур в коде нет. Имя файла без расширения становится адресом страницы
(`data/figures/<slug>.json` → `/figures/<slug>/`), поэтому в нём только
строчные латинские буквы, цифры и дефисы.

Имя файла начинается с обозначения фигуры: `di-02-circle.json` — фигура
DI 02.

Разделы каталога (`/disciplines/<discipline>/`) выводятся из тех же файлов:
раздел на сайте — это значение поля `discipline`, которое встретилось хотя бы
у одной фигуры. Страницы своего списка разделов не ведут; название раздела
собирается из значения поля (`dual-line-individual` → «Dual-line Individual»).
Какие значения поле вообще принимает, решает формат: список разделов один —
`lib/disciplines.json`, он задаёт префикс и порядок, и его читают и
`lib/figures.ts`, и `scripts/check-export.mjs`. Новая дисциплина — это строка в
нём и в таблице `data/figures/README.md`; страницы править не нужно, пока
имя раздела начинается с `dual-line-` или `multi-line-`: по этому началу
страница фигуры и `scripts/check-export.mjs` выбирают силуэт кайта. Раздел в
данных, которого в списке нет, роняет тест `lib/disciplines.test.ts`. Страница
фигуры в адрес раздела не вложена: она остаётся на `/figures/<slug>/`.

Поиск работает в браузере по `search-index.json`. В индексе только имя файла
фигуры (`slug`), обозначение, название и отметка о выведенной фигуре; описания
и геометрию туда не класть — его качает каждый, кто ищет. Адреса страниц
собирает `lib/paths.ts` — и для страниц, и для выдачи поиска.

**Формат файла описан в `data/figures/README.md` — читать до любой работы с
данными, схемами или страницами.** В записи фигуры — раздел, номер, название,
статус, ссылка на первоисточник (документ, версия, страница, дата чтения) и
геометрия в сетке окна: путь кайта по шагам, дуги, остановки, посадки. Формат
один на все шесть разделов книги; наполнены все шесть.

Битый файл, незнакомое поле, страница вне документа, дуга, которая не
сходится, и всё, что названо `*.json`, но обычным файлом не является, роняют
тесты и сборку с именем файла — пропускать их молча нельзя. Геометрию не
выдумывают: чего нет на странице первоисточника, то записывается как
`not_found` с причиной либо помечается в данных (`basis`, `unmarked`).

В реестре первоисточников два документа, и порядок значим: первый — книга
версии 3.0, действующая; второй — версия 2.2.1, прежняя. С прежней сняты
только четыре выведенные фигуры, у которых в версии 3.0 нет страницы
(DT 14, DT 15, MI 18, MP 05); действующие фигуры по ней не правятся. Страница
такой фигуры несёт две отметки — что фигура выведена и с какой редакции снята
схема (`class="edition"`); эту границу держат тест каталога и
`check:export`.

Что можно и чего нельзя класть в данные — в `docs/sources.md`. Коротко:
диаграммы из правил не перепубликуются, схемы рисуются из своих данных в
обозначениях книги, тексты описаний не копируются, ссылка ведёт на официальный документ.

## Гейт и сборка

Нужны node 22 и `python3` (только стандартная библиотека).

```sh
npm ci          # один раз и после смены package-lock.json
npm run gate    # гейт: всё, что гоняет CI
```

`npm run gate` — это по порядку `lint` (eslint), `typecheck` (`next typegen`,
затем tsc), `test` (vitest: формат и данные каталога фигур, разделы, поиск), `test:automerge` (unittest:
решение об авто-мерже и проводка воркфлоу), `build` и `check:export`. CI
гоняет те же команды отдельными шагами; меняя состав гейта, правь и
`package.json`, и `.github/workflows/ci.yml` — их совпадение держит тест
`scripts/tests/test_ci_wiring.py`.

Собрать статику:

```sh
npm run build   # готовый сайт — папка out/
```

`out/` в git не лежит. Страницы экспортируются как `<путь>/index.html`
(`trailingSlash: true`), так что веб-серверу не нужны правила переписывания.
`npm run check:export` после сборки проверяет, что в `out/` есть главная и
ровно по странице на каждый файл из `data/figures/`, а на странице — заголовок,
описание и ссылка на первоисточник с номером страницы, а отметка о прежней
редакции стоит ровно у тех фигур, что с неё сняты. Он же сверяет с данными
разделы: главная называет каждую дисциплину с числом её фигур и не ссылается
на фигуры напрямую, у каждой дисциплины своя страница со своим списком, со
страницы фигуры есть переход в её раздел и к соседям, а в
`out/search-index.json` — запись на каждую фигуру и ни одного лишнего поля.
Про поиск скрипт знает только то, что видно в файлах: поле есть в шапке каждой
страницы, индекс собран, клиентский код просит его по тому же адресу. Что
поле действительно ищет, гейт не проверяет — браузера в нём нет.

## Схемы

Схема рисуется на сборке из геометрии фигуры, в SVG прямо в странице; файлов
картинок в репозитории нет и быть не должно. На вариант фигуры — одна схема,
рядом — шаги каждого кайта словами.

- **Обозначения — как в книге фигур** (решение владельца). Графической
  легенды в книге нет, словарь снят с её схем; таблица «у нас — в книге» и
  список своих обозначений — в `docs/sources.md`, раздел «Обозначения схем».
  Берётся только условность: ни одна схема книги не срисовывается, каждый
  значок — формула в `lib/diagram.ts`.
- **Значок кайта стоит носом в точке и смотрит по курсу** — дельта у
  двухстропных, прямая кромка с парусом у четырёхстропных (MI, MP, MT): на
  входе (залит), выходе (пуст), остановке и в пути. Значок в пути не ставится
  на шаг, у начала или конца которого уже стоит значок того же кайта с тем же
  носом.
- **В остановке значок смотрит по курсу метки книги** — поле `nose` отметки
  `stall`, а не курс, выведенный из пути. Где книга метку не ставит
  (`not_found`), значка нет, подпись остановки остаётся.
- **Вспомогательная линия книги** (`guides` варианта) — у нас тонкий серый пунктир
  под путями со строкой в легенде; есть только у MT 01 и DT 11.
- **Значки уступают друг другу место.** Выход в точке входа или остановки с
  тем же курсом — кольцом вокруг них (у земли значок внутри поднят вместе с
  кольцом), с другим курсом — просто крупнее. Кайт в пути обходит значки
  координат, вход, выход и остановку, а где шаг короток — отходит значок
  координаты; на общем отрезке строя значки в пути уменьшаются. Знак поворота
  обходит значки координат. Полностью наложения не исключены: сколько их
  остаётся в каталоге, держит тест «наложения значков на схемах каталога» в
  `lib/diagram.test.ts` — меняя расстановку, смотри на его числа.
- **Направление.** У четырёхстропных — тонкая стрелка рядом с линией, справа
  по ходу, на каждом шаге: на самой линии встречные проходы сливались бы. У
  двухстропных кайт летит носом вперёд, и направление показывает значок в
  пути; стрелку получает только шаг, который он летит не носом вперёд.
- **Шаг `unmarked` знака направления не получает** — ни стрелки, ни значка в
  пути: книга его не показывает. Линия нарисована, в шагах стоит пометка
  «направление в книге не показано».
- **Поворот со смещением — не пролёт.** Поворот вокруг законцовки сам
  перемещает кайт (поле `to` шага `rotate`). Линия кайта на нём рвётся, а
  между точками стоит тонкая дуга — путь носа вокруг точки поворота — со
  стрелкой и углом; своя строка в шагах и в легенде. Отрезком такое смещение
  не записывается и прямой не рисуется. В начале и в конце такого поворота
  стоит значок кайта — если курс носа перед поворотом известен из пути.
- **Незаданное книгой числом не становится.** Величина, которую книга прямо
  объявила незаданной (`unspecified`; в каталоге — пять у MI 02), в данных
  числа не имеет. Кайт на схеме стоит по размаху нашего значка (`REV_SPAN`),
  место отмечено ромбом, линии сетки и числа у рамки у него нет, в шагах —
  «не задано». Замером метки книги такое место не подменяется.
- **Точка поворота названа у каждого поворота** — словом и тем, откуда оно
  взято (`about`, `about_basis`), либо записью `not_found`. В шагах выведенная
  отличается от прочитанной словами «выведено, книгой не названо».
- **События подписаны словами книги:** «Stop», «Stall», «Launch», «2-point
  landing», «½ Axel»; поворот на месте — дужка со стрелкой и угол. Легенда
  схемы переводит слова, которые на ней есть. «In» и «Out» стоят на каждой
  схеме, у нескольких кайтов к ним добавлен «#номер» цветом кайта.
- **Координата не с подписей схемы отмечена.** `derived` — кружок,
  `measured` — квадрат, `unspecified` — ромб; те же значки стоят в конце
  строки шага и объяснены в
  легенде. `text` на чертеже значка не имеет, пометка только в шагах.
- Где кайты летят по одной линии, их штрихи накладываются и без цвета
  сливаются; там порядок читается по номерам у входа и выхода и по шагам.
- Кайты команды различаются цветом, а без него — штрихом линии и номером у
  входа и выхода; вход от выхода — заливкой: схема обязана читаться без
  цвета.
- Вид посадок, одновременность и курс носа там, где значка в пути нет, — в
  шагах.

`npm run check:export` сверяет собранную страницу с файлом данных: схем
столько, сколько вариантов, линий и списков шагов — сколько кайтов; стрелок у
четырёхстропных — сколько шагов с известным направлением, у двухстропных —
сколько таких шагов не носом вперёд; значков входа и выхода — сколько
кайтов, остановок — сколько разных сочетаний «кайт, точка, курс» среди
отметок с курсом носа из книги (две остановки в одной точке с одним курсом —
один значок, как у MI 34), и каждая стоит в своей точке по своему курсу; вспомогательных линий — сколько в данных; дуг поворота со смещением — сколько таких поворотов, каждая
кончается в своей точке, а линия кайта рвётся на каждом из них и нигде больше;
точка каждого поворота названа в шагах так, как записана;
значков кайта в пути не больше, чем
шагов с направлением и концов поворотов со смещением, и у каждого такого
конца с известным курсом значок стоит; у незаданной величины нет ни линии
сетки, ни числа у рамки, а в шагах знаков ◇ и слов «не задано» — сколько
таких величин, и числа, которым проверка сама разрешила такое место, там
нет (сколько ромбов на схеме и куда смотрит нос значка у поворота, держат
тесты `lib/diagram.test.ts`); пометок
«направление в книге не показано» — сколько шагов `unmarked`; на странице
без геометрии схемы нет и названа причина (таких фигур в каталоге сейчас
нет, и эту ветку страницы живые данные не исполняют). Он же сверяет значки, слова и
легенду каждой схемы с данными, штрихи линий и классы цвета подписей,
заголовок и страницу варианта и заметки о геометрии. Где именно стоит значок
в пути и когда он пропущен, проверяют тесты `lib/diagram.test.ts`: по
собранной странице видно число значков, но не шаг, на котором каждый стоит.

Локальная разработка — `npm run dev`, сайт на `http://localhost:3000`.

## Как правка попадает в main

Обычный путь — PR; мерж только сквошем, заголовок PR становится коммитом в
`main`. Заголовки — Conventional Commits.

Зелёный PR вливает сам репозиторий — `automerge.yml` по завершении CI. Условия
в `scripts/automerge.py`, и все четыре обязательны: PR открыт владельцем
репозитория из ветки этого же репозитория; все проверки на голове завершились
и зелёные; GitHub считает PR mergeable, `mergeStateStatus` равен `CLEAN`; PR не
черновик и без метки `hold`.

- Придержать PR — метка `hold` или черновик. Ни снятие метки, ни перевод из
  черновика CI не перезапускают, поэтому после них: Actions → Automerge → Run
  workflow, ветка `main`, номер PR. С любой другой ветки ручной запуск
  пропускается.
- Прогон Automerge зелёный, когда PR влит или придержан штатно (черновик,
  `hold`, чужой PR, голова ушла вперёд). Красный — PR застрял и без человека
  не сдвинется: красная или отменённая проверка на голове помимо самого CI,
  конфликт с `main`, GitHub так и не отдал `CLEAN`, мерж отклонён. Когда
  красен сам CI, джоба Automerge пропускается: чинить надо CI.
- Отменённый прогон CI остаётся на голове навсегда, даже если рядом есть
  зелёный: его надо перезапустить (Re-run) или запушить новый коммит.
- После мержа соседнего PR GitHub около минуты отдаёт `mergeStateStatus:
  UNKNOWN` — скрипт это пережидает опросом. Конфликт с `main` он не чинит:
  нужен rebase и новый прогон CI.
- Дерево после чужого мержа не перепроверяется: PR, зелёный на прежнем `main`,
  вливается без нового прогона на текущем. И сам влитый коммит прогона CI на
  `main` по событию пуша не получает: мерж делает токен Actions, а его события
  воркфлоу не запускают. По той же причине на пуш в `main` нельзя вешать то,
  что должно сработать после авто-мержа. Из правила два исключения —
  `workflow_dispatch` и `repository_dispatch`: запуск воркфлоу тем же токеном
  прогон создаёт. На этом стоит довоз (`catchup.yml`, раздел «Выкат»): он сам
  запускает CI на `main` у влитого коммита, и дерево после мержа проверяется
  там — до выката, но уже после мержа. Но и у такого прогона завершение
  события `workflow_run` не порождает (измерено: CI, запущенный токеном,
  позеленел, и ни Deploy, ни Automerge на него не отозвались) — цепочку за
  ним надо вести самому, ручными запусками. Проверить `main` руками: Actions
  → CI → Run workflow.
- В счёт идут все прогоны на голове PR, чьи бы они ни были. Репозиторий
  публичный, и PR из форка с тем же коммитом может положить на эту голову
  свой незавершённый или отменённый прогон — тогда авто-мерж откажет до
  нового коммита. Отказ в безопасную сторону; на живом форке не проверено.
- `gh pr merge --auto` в воркфлоу не возвращать: он не ждёт проверок.
- Правка `automerge.yml` на своём PR не исполняется: `workflow_run` берёт
  воркфлоу из ветки по умолчанию. Решение проверяется тестами и прогоном
  `python3 scripts/automerge.py --repo OWNER/REPO --pr N --dry-run`.
- Правка `ci.yml` на PR, наоборот, исполняется сразу — `pull_request` берёт
  воркфлоу из ветки PR, и PR, выкинувший шаги из CI, зелёным и останется.
  Состав шагов сверяет с гейтом тест `scripts/tests/test_ci_wiring.py`.
- PR, который правит `.github/workflows/`, авто-мерж вливает как любой
  другой: отсутствие у токена Actions права `workflows` сквош-мержу через
  API не мешает (проверено прогоном: PR #7 с четырьмя файлами воркфлоу влит
  токеном).

## Выкат

Сайт живёт на `https://kites.malaev.net/`. Выкатывает его `deploy.yml`: после
зелёного прогона CI на пуш в `main` он собирает статику этого коммита и отдаёт
собранную папку плейбуку выкладки, который лежит в отдельном репозитории
инфраструктуры. Последний шаг читает с хоста выложенную ревизию и краснеет,
если она не равна выкатываемому sha.

- **Выкатывается только голова `main`.** Прогон коммита, который уже не
  голова (два пуша подряд, Re-run старого прогона), зелёный, но ничего не
  выкатывает: в его сводке написано «Выкат пропущен», сайт довозит прогон
  более нового коммита. Поэтому зелёный Deploy значит «на сайте этот коммит»
  только вместе со сводкой «Выкат» и двумя одинаковыми sha в ней.
- **Коммит, влитый авто-мержем, довозит `catchup.yml`.** Прогона CI на `main`
  по пушу у такого коммита нет (см. выше), а выкат слушает именно CI. Довоз
  читает с хоста выложенную ревизию и сверяет её с головой `main`. Совпали —
  на этом всё. Разошлись — решает `scripts/catchup.py`: у головы нет прогона
  CI на `main` — запустить CI, дождаться его и, если он зелёный, запустить
  Deploy; CI на `main` уже зелёный — запустить Deploy; идёт CI, запущенный
  вручную, — проследить за ним и выкатить самому; идёт CI по пушу — отойти,
  он довезёт сам; идёт выкат — отойти, а если довоз уже следит за своей
  головой, переждать его и выкатить следом; CI на `main` красный — прогон
  довоза красный, и без человека голова на сайт не попадёт.
- Довоз запускается после каждого успешного прогона Automerge и вручную с
  `main`. Раз в час его тем же ручным запуском зовёт `catchup-schedule.yml` —
  страховка: потерянное событие, оборванная цепочка, раннер лежал дольше
  суток. Расписание GitHub не точное, запуск может опоздать на десятки минут.
- **Расписание живёт в отдельном файле нарочно, и в `catchup.yml` его
  переносить нельзя.** Воркфлоу с расписанием GitHub отключает целиком после
  60 дней без активности в репозитории — со всеми его триггерами. Так
  отключится только страховка; включить обратно: Actions → Catch-up schedule
  → Enable workflow. Довоз после Automerge от этого не зависит.
- Красный выкат довоз повторяет на каждом заходе, то есть раз в час, пока
  выкат не пройдёт или голова `main` не сменится.
- **Откат сайта плейбуком довоз отменит на ближайшем заходе**: на хосте
  окажется не голова `main`, CI у головы зелёный — он выкатит её снова.
  Чтобы откат держался, сначала отключить оба воркфлоу (Actions → Catch-up и
  Catch-up schedule → Disable workflow) либо откатить сам `main`.
- Сам довоз ничего не выкатывает. Его джоба `state` идёт на раннере выката
  только затем, чтобы прочитать ревизию с хоста: в ней нет ни чекаута, ни
  кода репозитория. Запускает воркфлоу вторая джоба, на `ubuntu-latest`.
- Deploy по событию принимает только CI по пушу в `main`. CI, запущенный на
  `main` вручную, сам ничего не выкатывает; голову после него довезёт довоз
  (ближайший его заход либо ручной запуск Catch-up) или ручной Deploy.
- Ручной Deploy запускается только с `main` и только для головы с зелёным
  прогоном CI на `main`. Нужен новый запуск, а не Re-run старого.
- Джоба выката идёт на своём раннере с меткой `kites-deploy`; вместе с джобой
  `state` довоза это два исключения из правила про `ubuntu-latest` ниже. Раннер стоит на машине, где
  лежат ключи инфраструктуры; в секреты GitHub они не копируются. Если он не
  поднят, джоба не краснеет, а висит в `queued`.
- Условия, при которых код попадает на эту машину, держит тест
  `scripts/tests/test_deploy_wiring.py`: запуск — только `workflow_run` от CI
  с `event == 'push'` из этого же репозитория либо ручной с `main`; коммит —
  голова `main`; код репозитория исполняется только в контейнере сборки,
  которому чекаут смонтирован на чтение. Про довоз то же держит
  `scripts/tests/test_catchup_wiring.py`, и он же — саму цепочку: имена
  воркфлоу, событие, по которому Automerge будит Catch-up, запуски, которыми
  Catch-up зовёт CI и Deploy, и выходы, которыми джоба `state` говорит
  второй джобе «довозить». Тест читает текст файлов: что GitHub на эти
  события действительно отвечает прогонами, показывает только живой мерж.
- **Тест держит только `main`.** На `pull_request` GitHub берёт воркфлоу из
  ветки PR, и PR, вписавший метку `kites-deploy` в `ci.yml`, исполнился бы на
  той машине раньше, чем кто-либо увидит красный тест. От форка это закрывает
  настройка Actions «одобрение запусков для всех внешних участников» — её не
  снимать, а запуск чужого PR не одобрять, не прочитав его правки в
  `.github/workflows/`. От ветки в самом репозитории не закрывает ничего:
  право пуша сюда равно праву исполнять код на машине выката.
- Сборка в выкате — те же `npm ci`, `npm run build` и `npm run check:export`,
  что в CI.

## Что запрещено

1. Чужие диаграммы и тексты правил в репозитории — см. `docs/sources.md`.
2. Секреты и всё локальное в коммитах: имена машин, домашние пути, адреса.
3. Self-hosted раннеры: все джобы идут на `ubuntu-latest`. Исключений два —
   джоба выката в `deploy.yml` и джоба `state` в `catchup.yml` (раздел
   «Выкат»); ни одна джоба, запускаемая
   событием `pull_request`, на свой раннер целиться не должна.
4. AI-атрибуция в коммитах и описаниях PR: сообщение состоит только из
   описания изменения.
